## Commitment

The purpose of the IG Publisher is to produce HTML: implementation guides.
However, the IG Publisher does not produce the final pages on its own. It
generates HTML fragments (resource renderings, tables, narratives, QA
reports etc.), and the final pages are assembled and styled by the IG
**template**, which provides the page layout, navigation, CSS and scripts.

So the IG Publisher's accessibility commitment is this: the fragments it
produces allow templates to create implementation guides that meet the
[Web Content Accessibility Guidelines (WCAG) 2.0](https://www.w3.org/TR/WCAG20/)
at Level AA, at least.

Our approach is to make the default fragments accessible wherever we can do
so without significantly degrading the usual user experience (e.g. semantic
markup, table headers, text alternatives for images, not relying on colour
alone).

Where meeting the guidelines would make the usual experience significantly
worse, IG authors can switch the generated fragments to a form that does
meet them by setting the IG parameter `wcag-conformant` to `true`.

## Templates

The preferred template for producing accessible IGs is
**fhir2.base.template** (and templates derived from it). Other templates may
or may not deliver accessible output; their accessibility is the
responsibility of their maintainers.

Whatever template is used, the template is responsible for:

* The page structure: page language, title, landmarks, heading hierarchy,
  skip links and navigation
* The CSS: colour, contrast, focus indication, spacing and table presentation
* Any scripts and interactive features it adds

## Scope

### In scope

* HTML fragments generated by the IG Publisher (directly, and through the
  renderers in the [core library](https://github.com/hapifhir/org.hl7.fhir.core),
  which has its own ACCESSIBILITY.md)
* The `wcag-conformant` option
* The accessibility checks the IG Publisher performs on the built IG (see
  below)

### Not in scope

* IG templates, which are maintained separately (see above)
* Content written by IG authors (pages, narratives, images, diagrams).
  Authors are responsible for the accessibility of their own content - the
  checks below are there to help them
* The IG Publisher's command line and GUI tooling

## Accessibility Checks

The IG Publisher can help IG authors check their IGs. When the IG parameter
`accessibility-checks` is set to `true`:

* Every page in the built IG is inspected for common accessibility problems
  (e.g. missing page language or title, images without alt text, unlabelled
  form controls, broken id references, invalid language codes), and these
  are reported in the QA report
* For local (manual) builds, each content page also gets an accessibility
  check panel that runs [axe-core](https://github.com/dequelabs/axe-core) on
  the page as rendered in the browser

These checks help find problems; they are not a substitute for a full
accessibility evaluation.

## Conformance Status

**Believed conformant when used with an accessible template, tested on
published IGs.**

Conformance is not tested on the IG Publisher itself. It is tested on
published implementation guides built with it, and some of those IGs (e.g.
[US Quality Core](https://github.com/FHIR/us-quality-core)) test as fully
conformant to WCAG 2.0 and later. More examples will be added over time.

On that basis we believe the IG Publisher can produce conformant IGs when
used with an accessible template (such as fhir2.base.template) and accessible
author content. This is not a formal conformance claim for any particular IG.

## Known Limitations

None currently known. Issues found in testing will be tracked as GitHub
issues and listed here.

## Reporting an Accessibility Barrier

If you find an accessibility problem in an IG, please first work out where
it comes from:

* **The page layout, navigation, colours or styling** - report it to the
  maintainers of the template the IG uses
* **The content the IG author wrote** - report it to the IG's authors
* **A generated table, rendering or other fragment** - report it here:
  [create an issue](https://github.com/HL7/fhir-ig-publisher/issues/new/choose)
  and include "Accessibility" in the title

Helpful details include:

* The URL of the page, and the IG and template (with versions)
* Whether `wcag-conformant` was set
* The accessibility checker, browser and assistive technology (and versions) used
* What happened, and what you expected

Accessibility issues are treated as bugs, not feature requests.

## Contributor Requirements

When changing code that generates HTML, please:

* Use semantic HTML (headings, lists, `<table>` with `<th>`/`scope`)
* Provide text alternatives (`alt`, `title`) for images and icons
* Don't rely on colour alone to convey meaning
* Use CSS classes rather than hard-coded inline styles for colour and
  contrast, so templates can control presentation
* Check the output with `wcag-conformant` both on and off, and with
  `accessibility-checks` turned on
