* Multi-version packages: a core value set copied into another version's package (e.g. the R4 package of the extensions IG) no longer stays pinned to a source-version code system or value set that isn't copied with it: where the target version's core has it, the pin is changed to the target's version (value-filter-comparator was pinned to search-comparator|5.0.0, which R4 packages don't have)
* IG parameter `r5-bundle-relative-reference-policy` removed: the R5 rules for resolving relative references in bundles now apply to all FHIR versions (an IG that still sets it gets an unknown parameter warning)
* IG parameter `path-tx-cache` must name a folder inside the IG's folder (the one ig.ini is in): one outside it (an absolute path elsewhere, a path with .., or a symbolic link out) is ignored, with an error in qa.html, and the default (txCache) is used. The publisher deletes files in that folder
* The IG's temp, output and qa folders and its source folders (resources, pages, test, data, other, factories) must really be inside the IG's folder: symbolic links are followed when checking, so a folder (or a folder on its path) that links somewhere else stops the build. The publisher clears temp and output, so a linked output could delete files anywhere
* View definitions: resolve() now finds contained resources (#id references), and a Type/id reference only resolves when it's the type asked for
* QA: qa-dep.html asks both package servers for the IGs that depend on this one (only the secondary was being asked, and not every server answers that query), and says so when neither knows of any
* IG parameter `instance-hyperlinks` (yes | no | examples-only, default yes): whether the HTML renderings of instances in XML, JSON and Turtle link element names, types and references to their definitions. The links make the pages much bigger (#1382)
* StructureDefinition: new StructureDefinition-{id}-mappings.csv - a column for each mapping (and its comments), and a row for every snapshot element by id, with the values as they are in the definitions (#1171)
* StructureDefinition: the classic mappings rendering (a table for each mapping) is available again as the maps-classic, maps-classic-all, maps-classic-diff and maps-classic-diff-all fragments
* StructureDefinition: key elements now always include Narrative elements (#1106) and elements whose binding (or required/extensible/maximum/minimum/current additional binding) differs from the base; and the ancestors of elements in the differential are worked out correctly
* StructureDefinition: the terminology bindings and constraints tables leave out elements inside a prohibited (max = 0) element (#1110), and the bindings table has a documentation column when a binding has a description
* StructureDefinition: relative links in the descriptions of core search parameters now point into the base specification
* Dependency table: the reason for a dependency is rendered as markdown (#655)
* ValueSet: the list of value sets that include or exclude this one names each value set once (#1296)
* CodeSystem: new nsinfo fragment - the identifiers for the code system found in NamingSystem resources (#455)
* NamingSystem: new NamingSystem-{id}-xref fragment - the value sets that use the code system the NamingSystem identifies. It's always generated (empty unless kind = codesystem) so templates can include it unconditionally (#1187)
* Jekyll can no longer run ruby from IG or template content: it is always run with --safe (no _plugins/ or plugins_dir, no symlinks) and an explicit --source (so _config.yml can't point it at another folder), with a publisher config file read last that empties plugins and whitelist (safe mode still loads anything in both, and that can be a path), and with JEKYLL_NO_BUNDLER_REQUIRE set so a Gemfile in the folder is not evaluated. The publisher refuses to run Jekyll at all if there is a Gemfile or gems.rb in the folder it runs in
* Templates: the ant script of a template that isn't trusted is no longer parsed at all. Ant runs any tasks outside a target as it parses the build file, so until now an untrusted template's top-level tasks ran on the ci-build even though its targets were refused
* Templates: a template in the IG's own folder (template = #template) now follows the same rules as any other template that isn't trusted: on the ci-build it can't have active content (a script, or files other than the harmless kinds). Until now it wasn't checked at all
* Templates: a pre-process transform (an xslt the publisher runs over the IG's pages) is now active content, like an ant script: only a trusted template can have one on the ci-build, and the publisher refuses to load one from a template that isn't trusted
* Pre-process transforms can no longer write files: xsl:result-document is refused (they could already not read files or fetch anything). Transforms are only run by Saxon, since that's what makes the restriction possible
* Templates: any file in a template's scripts/ folder is now active content, whatever its extension (scripts read data files from there, e.g. groupings.txt), so a template that isn't trusted can't add or replace anything in it on the ci-build
* Templates: .po files (translations) are no longer active content
* Templates: a trusted template is only trusted as published - a released version (n.n.n), #current, or no version (the latest release). A branch build (current$branch), a dev build or a labelled version (e.g. -cibuild) of a trusted template, whether named by the IG or as another template's base, is treated as untrusted
* Templates: the trusted templates are listed in TrustedTemplates, with the GitHub repository each is built from. On the ci-build, a template that claims a trusted template's package id must be built from that repository (as the ci-build's -repo and -target, and the git origin, all say), and an IG can't claim one at all
* Templates: run locally, a template that runs scripts and isn't trusted no longer just runs: the publisher stops and explains, unless trustedTemplates in fhir-settings.json lists the template (or "all"). Run with -trust-template {id} (or -trust-template all) to trust it, and that is added to fhir-settings.json
* Templates: a dependency fetched from the IG's own location (not a package server) is no longer added to the package cache if it is a template, or if its package-list.json or package.json gives it the id of a trusted template. It goes into the cache under the id its package-list.json gives, so it could replace a trusted template for later builds that share the cache
* Template scripts can no longer read local files through an IG's XML: ant's xslt (and anything else that parses XML in the publisher's JVM) no longer reads external DTDs or entities. A file the IG supplies, such as input/includes/menu.xml, could use one to put any local file into its QA output. Set -Djavax.xml.accessExternalDTD=all to turn it back on
* Jekyll, when a ruby path is set: the command is no longer passed to bash as one string, so a folder the IG names (path-temp, path-output) can't run a shell command
* Windows: jekyll and sushi are run through cmd with NoDefaultCurrentDirectoryInExePath set, so cmd no longer runs a same-named command (e.g. jekyll.bat) from the folder it runs in instead of the one on the PATH
* Sushi: the sushi-version in an IG's fsh.ini must now be a plain version number (e.g. 3.16.0). It went to npx as fsh-sushi@{version}, and npm reads much more than a version there (another package, a git repository, a tarball URL), so an IG could choose any npm package to run. The command is also no longer passed to bash as one string when an npm path is set. Sushi is now run in an empty temporary folder (and told where the IG is), not in the IG's folder, since npm takes its .npmrc (which registry to install from) and node_modules from where it's run; an IG that has an .npmrc or a node_modules/fsh-sushi of its own is refused
